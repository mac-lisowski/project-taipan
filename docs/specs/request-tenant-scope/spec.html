Request-scoped tenant context

Tenant scope comes from the logged-in user: session cookie to user to tenant. No config tenant, no fallback. Spec: docs/specs/request-tenant-scope/spec.md.

Test seam

  • Tests cross the middleware through TestClient (lifespan running): register, login, /me, logout. They assert outcomes and rows, never the ContextVar.
  • /me reports the ambient scope, so it doubles as the scope probe.
  • Flush-guard test writes a tenant_id="b" row under scope "a" and expects a raise.
  • Startup check test asserts boot fails when encrypted columns exist and the module is unregistered.

Out of scope

Shared tenants, password reset, session management endpoints, rate limiting, per-tenant KMS keys, background-job helpers, crypto package changes.
