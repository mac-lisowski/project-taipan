Users Admin

Owner account administration. Details, activate, deactivate, delete. Spec: docs/specs/planned/users-admin/spec.md.

Action flows

flowchart TD O["system owner"] --> L["/users list row"] --> D["/users/:id details"] D -- "deactivate" --> V["revoke all sessions"] --> A["is_active false, login refused"] D -- "reactivate" --> B["is_active true, login works"] D -- "delete, confirm step" --> W["revoke all sessions"] --> R["row + profile + links gone"] A --> S["old session: 401"]

Module seam

flowchart LR W["web: /users/:id + users-admin lib"] -- "BFF" --> R["users router: owner guard"] R --> U["users service: detail, activate, remove"] U -- "revoke all" --> S["sessions seam"] U --> P["profile + roles + tenants joins"] Q["profiles router: session, self only"] --> U

No schema change. Guards tighten: users routes ask the system owner, profiles ask for a session and serve the self user only.

Depth: before and after

Before

users routes: any tenant admin
deactivated user keeps session
profiles: anonymous writes

After

users routes: system owner only
deactivate kills sessions, 401 after
profiles: session + self only

Test seam

  • API over HTTP, real test DB, fake KV. Guard, activation, delete, detail, and profile pins.
  • Session pins: revoked user gets 401, others survive, login matches the unknown-credentials answer.
  • Activation link for a deleted user answers the invalid-link shape, no 500.
  • Web lib with stubbed fetch: paths, mappings, state machines, pinned copy. No render tests.

Out of scope

Editing other profiles, role management, invites, personal tenant and key cleanup, audit and events, bulk actions, reset for inactive accounts, server paging.
