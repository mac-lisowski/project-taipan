LiteLLM gateway docker stack

Run the LiteLLM proxy from the docker quickstart in both dev stacks. Ship a pinned pull-through image for deployment. No API code touches the gateway yet. Prose lives in spec.md.

Shape

Both stacks get the same two services. The host stack owns port 4000. The devcontainer stack publishes no port, like Infisical on 8080. One Dockerfile pins the image tag for every environment.

Key decisions

Pull-through pin

One new pull-through image file beside the Infisical one pins litellm:v1.104.0. The gateway service builds from it in both stacks. Railway uses it too. An upgrade is a one-line tag edit.

Quickstart environment

Master key with a committed dev default, salt key with a stable dev default, database URL, and models stored in the database. Real values come from Railway variables.

Dedicated database

litellm-db runs the repo-standard Postgres 17 on its own volume per stack. It health-checks with pg_isready and publishes no port. The gateway starts only when it is healthy.

Parity rule

Both compose files mirror each other, as the Infisical blocks already do. Only the host stack serves a browser; the devcontainer serves the in-network address the API will use later.

Test seam

No code seam moves, so no pytest or vitest file changes. The seam is the running stack. Four checks cross it, in order:

Check crossesAsserts
Compose parsedocker compose config exits clean on both files
Docker gatescripts/check-docker.sh passes with the new file

Bring-upDatabase turns healthy. Liveliness answers I'm alive!. UI serves. No key means 401, master key passes auth

No provider key is needed for any check. A master-key chat call without a model fails for lack of a model, which still proves the gateway is up.

Out of scope

API integration, model and provider setup, virtual keys and budgets, Redis and observability, Railway dashboard wiring, new CI jobs, and production hardening. Details in spec.md.
